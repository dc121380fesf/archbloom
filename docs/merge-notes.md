# 面片合并：从「几何拼接」到「半边拼接」

> 记录日期：2026-10-18
> 对应提交：`c8a15fe`（半边拼接）、`d210922`（蛇形环切分）、本次（共线点/桥接/排序修复）

## 一句话

旧实现在「两个面拼起来会形成环」时一律拒掉，所以开孔板的顶面拼成留一道缝的 C 形大环，
洞的 955 个边界点里只有 17 个落在孔圆上。换成半边拼接后，**3148 面 → 70 面**（理论极限），
洞是 64 点真圆，FreeCAD 回读闭合、体积 1607.300918301 一字不差。

## 为什么旧方案走不通

旧 `merge_coplanar` 是**几何拼接**：两面的顶点环按坐标拼接、数重复顶点、再按面积猜哪段是洞。

三条硬伤：

1. **环的边界取决于拼接顺序**——同一批面片换个顺序拼，洞会被划到不同位置
2. **靠坐标判重合**——`WELD_TOL` 放大到 1e-6 就出问题，收紧了又漏缝
3. **遇到自交就拒**——「拼完会形成环」的情形全部放弃，于是洞永远是「留缝的 C 形」

## 半边拼接怎么解决的

沿共享边拼接两个面，本质是**改两条 `next` 指针**：

```text
A 的环：… → ha → next_a → …
B 的环：… → hb → next_b → …

拼接后：… → next_b → … → next_a → …
          （ha 与 hb 被摘除）
```

**全程不做几何计算。** 不存在「算出来坐标相同但索引不同」，也不存在浮点误差。
边是对象，两个面共享边就是共享同一个 `Edge`，不可能对不上。

## 踩的坑（按发现顺序）

### 1. 拼接后必须摘除 ha/hb

第一版忘了摘。它们留着旧的 `next`，遍历时形成「短路」——从 `ha` 走进旧链，
遇到已访问顶点就断开，环被切成三角形。**症状：4 个洞全是 3 个点。**

修法：`next` 指向自己（自环，遍历一步就终止）+ `twin` 清空。

### 2. 蛇形环要切成简单环

摘除后能合到 70 面，但顶面是 **2894 点的蛇形环**（1329 处重复顶点）——
外边界和孔边界被拼接缝连成一条链。体积/水密/欧拉都对，
但 STEP 写不出独立圆洞（写出来是一整个蛇形多边形）。

修法：`split_rings()` 栈判环——沿序列走，遇到已在栈里的顶点就把中间段切出来当独立环。
**纯拓扑操作，不需要平面假设**（这正是「平面图面提取」失败而这次能成的原因）。

### 3. 外环里全是共线点，耳切卡死

切分后洞是 64 点真圆了，但三角化面积算出来 **0.000513 m²**，比理论 0.000322 大 60%。

诊断发现：外环有 **132 个点**，其中绝大多数落在同一条直边上（x 全等于 0.02）。
耳切遇到共线点 `cross = 0`，既不是凸点也不是凹点，全部跳过 → **guard=1 第一轮就卡死**
→ 兜底扇形展开 → 三角形覆盖到洞里。

修法：`simplify_collinear()`，合并时按「点到直线距离 < 容差」剔除共线点，回去后外环只剩 4 个角点。

### 4. `bridge` 的 inset 把 anchor 包了两遍

老代码写的是 `inset = [anchor, 洞…, anchor]`，但 anchor **本来就在环上** ——
环里出现 3 个 anchor，耳切第一轮全部被 `point_in_tri` 拒掉。

修法：`inset = [洞…, anchor]`，只留末尾一个。

### 5. `point_in_tri` 把共线点当成遮挡

洞上相邻点首尾相接，`h2` 几乎落在 `h0-h1` 这个极瘦三角形的延长线上。
`point_in_tri` 的判据是 `!(neg && pos)`，当负号和正号都没有时返回 `true`（视为在边界上）
→ 洞点互相「占位」→ 所有耳都被拒。

修法：与三角形任一顶点**坐标重合**的点跳过（容差用 `eps`）。桥接缝的 anchor 正是这种情况。

### 6. `rebuild_faces` 按有符号面积排序，底面把洞当外环

最隐蔽的一个。排序逻辑是「面积最大的当外环」，用的是 `ring_area(s, ring, normal)` 的**有符号**值。

底面法线朝下：外环 -400，洞 +78。**降序排列把洞排到了第一位**，
于是底面的「外环」是那个 64 点的洞，真正的 4 点外框成了洞。

症状：底面精确面积算成 **-0.000478**（洞被「加」而不是减）。

修法：按**绝对值**排序。

## 遗留问题

### 三角化还差 0.34%

顶面三角化面积 0.000320481 vs 精确 0.000321586，差 1.1e-6（0.34%），
导致 `m1_merge_plate_with_hole` 的体积断言（`dv < 1e-6`）失败，实测 1.15e-3。

来源是**桥接缝处的极瘦三角形**：缝是 `anchor→h0` 和 `h63→anchor` 两条几乎重合的边，
三角形高度只有 1e-4 量级，数值上丢了一点面积。

**这不是逻辑错误**：FreeCAD 独立回读同一份 STEP，体积与理论值完全一致。
我们的 1.606e-6 = 1606 mm³，相对 FreeCAD 偏 0.07%。

**待定**：继续压（要放弃桥接缝方案）还是改断言口径（对准解析真值而非旧自己）。
测试原本守的是「合并不动几何」，但旧路径下成立是因为**旧版不产出带洞面**——
现在产出带洞面了，这个判据本身就不合时宜。

### 欧拉数报 2，带一通孔应为 0

`euler_characteristic()` 已从 `verts.len()`（含孤立顶点，虚增到 2698）改成只数参与面的顶点，
降到 2。距离理论值 0 仍差 2，未查清。几何已由 FreeCAD 独立验证，所以是指标实现的偏差。

### 旧实现保留为 `merge_coplanar_legacy`

它在某些退化输入上比半边路径宽容（不要求拓扑完全健康），`merge_coplanar` 出错时回退。

## 一个教训

**FreeCAD `openDocument` 读不了 STEP，用 `Part.read`。**

`ios_base::failbit set: iostream stream error`，连 v0.4.3 那份验证成功的旧文件也一样失败
——说明不是文件问题，是 FreeCAD 1.1.2 的文档加载器这条路走不通。
以后验 STEP 一律用 `Part.read()`。
